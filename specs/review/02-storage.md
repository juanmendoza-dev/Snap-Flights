# Snapshot storage

### T1 — Part files are visible before completion and concurrent writers can overwrite
- **Severity:** high
- **Where:** `pipeline/store/paths.py:next_free_part_path`; `pipeline/store/snapshot_store.py:SnapshotStore.write`; commit `6bb00aa`.
- **What's wrong:** The writer checks whether a final filename exists and later writes directly to that filename. Selection and creation are not atomic. Readers glob final names while a footer is still being written. Two calls with the same run/partition can select the same name and truncate/overwrite each other's files. Different run IDs avoid that collision but do not avoid partial-file reads.
- **Why it matters:** An API request during cron collection can fail on an incomplete Parquet file. A crash or disk-full event leaves that file in every future scan. Concurrent window tasks under one run ID can lose records despite the append-only promise. Both races were reproduced with controlled scheduling.
- **Recommended fix:** Write to a unique temporary file in the target partition using a suffix excluded from scans; flush/close it, then atomically publish. Preserve no-overwrite semantics with an exclusive publish operation, or a per-partition lock covering filename allocation and publication. `os.replace` alone does not protect two writers that chose the same target. On POSIX, an exclusive hard-link publication of a completed same-filesystem temp file is one option. Clean abandoned temporary files by age. Add crash-before-publication and synchronized two-writer tests. Use a separate scheduler lock for run bookkeeping. A whole multi-partition transaction is optional, but document whether readers may see a partially completed run.
- **Confidence:** high — reproduced incomplete reads and identical target selection by two writers.

### T2 — Rejected-before-dedup is a store semantics defect with siblings
- **Severity:** high
- **Where:** `_build_query`; `sources_with_recent_data`; SF-05 Known store interaction; commit `b26c374`.
- **What's wrong:** Quality filters are applied before winner selection. An older `ok` row survives a later rejected version; explicit `data_quality=ok` can similarly resurrect an older row after it becomes `suspect`, and explicit `rejected` can return an obsolete rejection after a later recovery. The health query independently filters rejected rows and performs no dedup. The note's phrase “bad price resurfaces” overstates the evidence: an old valid $400 fare followed by a new invalid $0 fare does not prove $400 was bad. The issue is violating the promised latest-version view. A genuine reclassification also needs revision ordering; changing only quality leaves `fetched_at` unchanged.
- **Why it matters:** Prediction, audit reads and health can describe incompatible states. Moving only the default exclusion leaves explicit quality filters and health wrong. Calling this an SF-05-only fix conflicts with freezing the store before SF-05.
- **Recommended fix:** Decide in a short ADR that default reads select the latest daily version and then apply quality predicates. Put all quality predicates after `rn=1`, share that resolved relation with health, and add tests for `ok→rejected`, `ok→suspect`, `rejected→ok`, explicit quality selection, and same-observation reclassification. Keep natural-key-invariant filters before dedup for pushdown. Give timestamp upper bounds separate documented semantics: an explicit as-of cutoff may legitimately select an older version; filtering latest rows by timestamp is a different query. Do not blindly move every filter after ranking. Define revision ordering with T3 rather than making quality rank implicitly override chronology.
- **Confidence:** high — the default resurrection was reproduced; sibling behavior follows the same SQL.

### T3 — The dedup winner depends on batching and is not fully deterministic
- **Severity:** high
- **Where:** L0 §6; `write()` batch dictionary; `_build_query()` ranking; SF-03-build §2.8; commit `7f908b0`.
- **What's wrong:** Within a batch, list position wins; across files, later `fetched_at` wins. Writing `[18:00/$100, 06:00/$200]` together retains $200, while separate writes retain $100. Across files, `fetched_at DESC, ingest_run_id DESC` still ties when the same run writes two different payloads at the same timestamp. The supported `-002` retry suffix does not enter the ordering. A reproduced same-run tie retained the first price, not the later write.
- **Why it matters:** Changing scheduler batch size changes the history. Reprocessing quality under the same run/timestamp can be ignored. UUID lexical order is a deterministic arbitrary tie rule between distinct runs, not write chronology.
- **Recommended fix:** Specify one reducer used both within and across batches. Preserve later fetch time as the daily sampling rule. For equal fetch times, define an explicit revision/sequence for corrections and retries, or reject conflicting payloads with identical revision identity; exact duplicates can collapse. Do not silently choose a price-dependent tie winner. Add a property test that splitting/permuting batches produces the same logical result under the selected order. Persist enough ordering information to reproduce a correction without falsifying `fetched_at`.
- **Confidence:** high — batch dependence and the equal-run tie were reproduced.

### T4 — Partition pruning is discarded for a reason that does not apply to DuckDB
- **Severity:** medium
- **Where:** `paths.py:part_files/scan_glob`; `_scan_targets`; `_build_query`; SF-03-build §2.5; commits `b19dd5b`, `dadf673`.
- **What's wrong:** Each read enumerates and sorts every part merely to check existence, then DuckDB expands the full glob again. Route/date filters never narrow discovery. With Hive disabled, `fetched_date` becomes a cast of a stored timestamp rather than a partition predicate. File statistics may still prune row groups; that is not directory pruning. The documented dictionary/string collision applies to the observed PyArrow reader path, not inherently to DuckDB: the installed DuckDB 1.5.5 successfully read these parts with `hive_partitioning=true` and exposed their fetched-date partition.
- **Why it matters:** A small row volume can still create many files: one daily part per 20 source/route pairs is 7,300 files/year; writing each of 200 fast-flights calls separately can add 73,000/year. One-route requests and health pay global discovery/metadata costs. The single-file fixture cannot reveal this.
- **Recommended fix:** Keep self-describing columns. Pass filters into discovery and construct a narrowed explicit file list, or scan production parts with explicitly typed Hive columns and a partition-date predicate. Handle the nonpartitioned fixture in a separate relation if enabling Hive; do not blindly enable it on the mixed fixture/parts list. Pass the discovered paths directly instead of globbing twice. Benchmark 90/365 days of realistic part counts, record cold and warm timings, and aggregate writes by run/route when practical. Keep PyArrow's `partitioning=None` for the affected reader. Compaction can remain deferred until those measurements justify it.
- **Confidence:** high on unnecessary discovery and the incorrect DuckDB rationale; medium on latency impact until measured on the target VM.

### T5 — Fixture union silently blends synthetic and real history
- **Severity:** high
- **Where:** `_scan_targets`; SF-03-build §2.8 fixture union; `shared/settings.py`; SF-07 response contract.
- **What's wrong:** Fixture rows impersonate the real source enums and union into the same cohort with no synthetic provenance column. Turning the flag on affects all predictions, but only `/health` exposes the mode. “Real naturally supersedes fixture” is conditional: it requires the same full key and a later ordering value. A real 05:00 row loses to the fixture's 06:00 row; different stops/carriers create different IDs. Fixture history can dominate counts long after collection begins.
- **Why it matters:** A public prediction or backtest can claim source-backed high confidence mostly from generated prices. The caller receiving `/predict` has no reliable way to discover that from the payload.
- **Recommended fix:** Make `fixture_only` and `live_only` explicit, isolated dataset modes; use fixture-only for the demo and tests. If a hybrid mode is required later, attach dataset provenance at read time, keep separate statistics, expose synthetic counts and mode in each response/report, and specify precedence explicitly. Do not use synthetic rows to meet live confidence thresholds. Bind health's mode to the injected store settings, not a fresh environment read.
- **Confidence:** high — the union and missing row/prediction provenance are explicit.

### T6 — Physical schema pinning is enforced for fixtures but not live reads
- **Severity:** medium
- **Where:** `records_to_table`; `table_to_records`; `_build_query` `union_by_name=true`; `_conform`; `read()`.
- **What's wrong:** Live parts are merged with `union_by_name=true` and then cast into expected dtypes. `read()` casts before calling the strict Arrow converter, so that converter checks the manufactured result rather than the original file schema. `read_frame()` never checks record IDs, enum validity or schema version. A missing nullable field can be silently filled; an unsupported `schema_version=2` can reach models as ordinary v1 data.
- **Why it matters:** A second writer or schema migration can change the meaning/physical types while a prediction still appears to honor the frozen schema. Other bad files fail the entire scan only at query time.
- **Recommended fix:** Validate the batch before publication and reject unsupported versions. Record/validate a schema fingerprint per part or committed manifest; cache checks by immutable filename. Fail explicitly on unsupported schema versions, and apply versioned migrations only in named readers. Use `union_by_name` only for declared compatible evolution, not as a substitute for it. Add a wrong-version part and a missing-column part to read-path tests.
- **Confidence:** high — the live read path lacks the checks. No existing fixture corruption is alleged.
