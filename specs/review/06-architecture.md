# Architecture, collection and zero-cost operations

### A1 — Daily request caps and cooldowns do not survive cron restarts
- **Severity:** high
- **Where:** L0 §5 stateless-adapter rule; SF-02 daily cap and six-hour cooldown; SF-04 run generation/requeue; decision 0001 SQLite choice.
- **What's wrong:** The adapter must enforce a cap across all routes for the day and a cooldown spanning calls, while L0 allows only an in-process limiter. Cron starts a new process; manual runs and crash retries do too. There is no shared persisted reservation/count or circuit state. SF-04's “respect budgets” instruction supplies no transaction or overlap rule. SQLite was chosen for operational state, but SF-04 instead leaves queue/bookkeeping files unspecified.
- **Why it matters:** Two runs each spend their own 200-call allowance. Restarting a blocked scraper immediately forgets the six-hour cooldown. A failed write followed by a fresh run repeats upstream calls even though read dedup cannot refund them.
- **Recommended fix:** Use the already selected SQLite for day/source budgets, reservations, attempts, cooldown-until and resumable request coverage. Acquire a process-level scheduler lock for cron/manual runs; count every attempted upstream request, including retries, against the budget. Define conservative recovery for reserved-but-unknown attempts after a crash. Give adapters an explicit shared budget interface; keep pacing local but make cap/circuit state durable. Test process restart, UTC rollover, overlapping starts and partial-window retry. Persist queue state and part publication status so retries reconcile completed work.
- **Confidence:** high — in-memory state cannot enforce the cross-process promises.

### A2 — Zero-cost hosting has no concrete resource envelope
- **Severity:** medium
- **Where:** decision 0001 Backend hosting; absence of deployment/resource configuration.
- **What's wrong:** “Always Free ARM VM” does not pin shape size, tenancy type, region, storage or backups. Oracle's currently retrieved Always Free documentation lists 1,500 OCPU-hours and 9,000 GB-hours/month, equivalent to 2 OCPUs/12 GB for Always Free tenancies, plus 200 GB combined boot/block storage and five volume backups. Do not assume the older commonly quoted 4-OCPU/24-GB allowance. Account-specific eligibility remains unverified. [Oracle Always Free resources](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).
- **Why it matters:** A future deployment agent can allocate a paid shape/storage resource or plan workers against an unavailable memory budget. Trial credits are not a permanent $0 plan.
- **Recommended fix:** Add a minimal deployment decision with the actual console-confirmed tenancy limits, home region, Always Free-eligible image/shape, OCPU/RAM allocation, total boot/data/backups, and quota constraints. Budget API, collector and backtest memory together. Keep deployment acceptance contingent on that verified envelope. Record account-specific differences rather than guessing.
- **Confidence:** high that the deployment envelope is absent; medium on the applicable allowance until the account's console limits are supplied.

### A3 — Reprovisioning the VM does not recover the unique collected history
- **Severity:** high
- **Where:** decision 0001 reclaim warning; E1 deferred retention/backfill; SF-03 gitignored snapshots; no operational recovery spec.
- **What's wrong:** Infra reproducibility is requested, but there is no backup/restore policy for snapshots, quarantine, scheduler state or manifests. Disk/log growth and minimum free-space behavior are unspecified. Oracle documents both idle-instance reclamation and capacity unavailability; those make a local-only history a durability risk even if the code is reproducible. [Oracle compute conditions](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).
- **Why it matters:** Losing the only data volume removes the project's one non-reproducible asset. Fetching fares today cannot reconstruct what prices were on missed historical fetch days. Restoring code plus the synthetic fixture cannot restore a real backtest record.
- **Recommended fix:** Before unattended collection, define a bounded backup destination within verified free quotas, retention/rotation, checksums, and a tested restore procedure including SQLite state. Start with daily backups and an explicit acceptable loss window; record it. Monitor disk bytes/inodes and rotate logs; stop collection cleanly before exhausting space. Retain enough data for the trailing-year model and completed evaluation windows. Define backfill as recovering still-queryable coverage with the actual new receipt time; never backdate `fetched_at` to invent missed history. Preserve known gaps in coverage metadata.
- **Confidence:** high on missing recovery contracts; actual volume durability/backup configuration is not available for inspection.

### A4 — Public API work is unbounded even with a bounded response cache
- **Severity:** high
- **Where:** SF-07 out-of-scope rate limiting; SF-07-build cache and routes handlers; `SnapshotStore._connect/read_frame`; decision 0001 shared VM.
- **What's wrong:** The proposed 1,024-entry cache bounds stored responses, not expensive in-flight computations. Varying date or user-supplied price bypasses it. Each cold prediction opens a fresh in-memory DuckDB database and materializes history; `/routes` also reads history. There are no query/thread/memory limits or admission control. The six-hour key omits data/config revision, so an identical request can keep returning the pre-collection answer after new observations arrive. The <300 ms test is repeated warm calls on one fixture, which can exercise only cache hits.
- **Why it matters:** A few concurrent cold requests compete with cron for CPU/RAM and can exhaust a small free VM. A rejected fare or newly collected route can remain actionable/unknown in cache for six hours. No user account is needed to trigger either issue.
- **Recommended fix:** Specify bounded concurrent prediction work, request/body limits, timeout/cancellation, and per-process DuckDB/Polars resource settings sized to A2. Add single-flight computation for identical cache misses and a bounded feature cache keyed by dataset revision/config digest/as-of. Include data/config revision in response-cache keys, or define and expose an explicit bounded-staleness policy with refresh after collection. Add basic unauthenticated request throttling at the API/proxy layer before public deployment; this need not introduce accounts. Benchmark distinct cold requests and concurrent API+collection workloads, not only repeated hits.
- **Confidence:** high on missing bounds and cache invalidation; actual concurrency capacity needs ARM-VM measurement.

### A5 — Expected upstream failures have outcomes but no bounded retry policy
- **Severity:** medium
- **Where:** L0 §5; SF-01 failure mapping/pacing; SF-02 error/cooldown handling; SF-04 summary/error handling; SF-07 health.
- **What's wrong:** Outcomes exist, but timeout budgets, retry count/elapsed-time limits, retryable status classification, `Retry-After` bounds, pagination budgets and run deadlines are not pinned. Run summaries count failures but no observer/notification or last-success readiness signal is specified. `GET /health` is required always to report `ok`, and only recent sources are returned, hiding stale ones. An exit code in unattended cron is not a notification by itself.
- **Why it matters:** A hanging source occupies the collector indefinitely; a retry policy spends the cap on a single request. Collection can stop for weeks while process liveness remains green and the API serves cached history.
- **Recommended fix:** Pin connect/read/total deadlines, capped retries with jitter, explicit retryable statuses, bounded `Retry-After`, and an overall run deadline. Record attempted/completed/empty/failed date coverage, elapsed time and last successful collection per source. Separate cheap process liveness from readiness/freshness. Wire a local health check or available free notification transport to collection failure and stale-data signals; include a deliberate no-work-due outcome. Keep stale configured sources visible with status and last-seen time.
- **Confidence:** high on missing policies; suitable retry budgets depend on verified endpoint limits and observed latency.

### A6 — Source reliability assumptions have not been tested within the zero-dollar constraint
- **Severity:** medium
- **Where:** SF-01 Source facts/live smoke test; SF-02 Source facts/pinned dependency; E2 “works on day one” claim.
- **What's wrong:** No pinned fast-flights version, recorded provider responses or sustained coverage experiment exists. The current upstream README describes v3 APIs and optional external integrations; a dependency-name pin alone does not specify transport, fallback behavior or its resource/cost assumptions. [fast-flights upstream README](https://github.com/AWeirdDev/flights). The spec itself calls the scraper fragile, yet the fixture treats it as available every day.
- **Why it matters:** A one-route smoke test can succeed while repeated collection from Oracle's network is blocked or sparse. An agent may enable a browser/proxy/external-service fallback to improve reliability without a budgeted operational contract.
- **Recommended fix:** Pin the tested version and exact direct-fetch mode, inventory its runtime dependencies and fallbacks, and explicitly disable paid integrations for this product configuration. Run a small budgeted multi-day coverage study once access is available; store request counts, successful date coverage, cache ages and failures. Treat calendar-only operation and scraper-disabled operation as supported degraded modes. Keep source viability and sustained coverage as open evidence requirements until measured; do not claim live “ground truth” from the library name alone.
- **Confidence:** high on missing evidence/version; low on eventual source reliability, which requires real execution from the intended host.
