# Prediction and evaluation

SF-06/SF-07 are specifications, not implemented models. These findings describe failures an implementation would inherit by following them literally. Percentiles and medians are a reasonable first descriptive baseline; they do not by themselves establish predictive accuracy.

### P1 — Empty-data predictions cannot satisfy their response type
- **Severity:** blocker
- **Where:** SF-06-build §4.1 `Prediction`, `CurrentPrice`, `Basis`; §4.5 predictor steps 3/5; §8.2; SF-07-build `PredictResponse`.
- **What's wrong:** The empty-store/unknown-route branch promises a successful neutral prediction even when no current price exists. Both model and API require a non-null current price with positive amount. `Basis.from_` and `Basis.to` are also mandatory dates despite no observations. A sentinel percentile 50 is indistinguishable from a computed median rank. The documented thin-data constructor does not exist and cannot fill these fields honestly.
- **Why it matters:** The very first production request, before collection starts, either raises validation errors or fabricates a price and evidence dates to pass the wire contract.
- **Recommended fix:** Amend the contracts before SF-06: allow `current_price`, `price_percentile`, and basis date endpoints to be null when unavailable; use zero counts, empty sources, neutral/low, and a machine-readable unavailable reason plus explanatory note. Keep a supplied current price even when history is absent. Add model/API tests for empty store with and without user price, unknown route, known route/no observed departure, and thin-but-nonempty history. Regenerate OpenAPI from these branches rather than treating “fully populated” as “every field non-null.”
- **Confidence:** high — mutually incompatible type and behavior requirements.

### P2 — The verdict rules confuse a price-level difference with a future move
- **Severity:** high
- **Where:** SF-06-build §4.3 `find_expected_low`, §4.4 `decide_verdict`; commit `6f7c8a0`.
- **What's wrong:** The wait search includes today. With percentile 80, current price $500, and a curve starting at $400 and then rising, the rules say wait and return a window starting today. At departure-day zero, the only curve point can still produce wait. The book-now rule similarly uses the maximum anywhere in the curve relative to the quoted price, not a rise from the curve's current point. A flat $420 curve and a $390 quote satisfy a supposed 5% future rise. A large later maximum can also hide a much better earlier dip.
- **Why it matters:** The API tells a user to wait when the evidence only says their quote is above a typical price available now. Its “prices usually rise/dip” reason does not describe the calculation. Fixing `expected_low != None iff wait` resolved a shape invariant, not this decision error.
- **Recommended fix:** Define an actionable future purchase window strictly after `as_of` and before a documented booking deadline. Compute future movement against the supported curve value at the current horizon, while keeping quote-vs-history cheapness as a separate condition. Require a future supported dip for wait; choose `expected_low` from exactly those eligible points. At zero remaining purchase days, never wait. Add explicit tests for rising-from-today-minimum, flat-but-below-quote, departure today, and early-dip/later-spike curves. Pin the desired book-now treatment of an intervening dip in an ADR.
- **Confidence:** high — concrete counterexamples satisfy the specified inequalities. Product choice of a booking deadline still needs a decision.

### P3 — Missing curve cells break horizon and confidence guarantees
- **Severity:** high
- **Where:** SF-06-build §4.3 curve construction/smoothing and `find_expected_low`; §8.5 frozen interface.
- **What's wrong:** Missing seasonal cells fall back to a bucket median without a minimum-count requirement. Missing bucket cells are omitted entirely. The frozen contract nevertheless says the curve starts at `dtd_now` and is empty only for past trips or no usable route history. `find_expected_low` infers today from the first surviving point: if a dtd-100 query first has data at dtd 60, its 60-day search reaches departure rather than stopping at dtd 40. Rolling over surviving rows treats gaps as adjacent days. Confidence depends only on today's broad bucket, regardless of future support or seasonal fallback.
- **Why it matters:** A deep current bucket plus one future observation can generate a high-confidence wait. The expected-low window can lie beyond the verdict's horizon; gaps can be smoothed into unsupported purchase dates. Far-out trips in the single `90+` bucket also get a flat curve based on fixture observations only out to 120 days, despite API acceptance out to 365.
- **Recommended fix:** Carry `as_of`/`dtd_now` explicitly in a curve result along with point-level support count, fallback level and missing ranges. Use a calendar-indexed grid; never smooth across unsupported gaps. Apply minimum support to broad fallbacks too. Use the actual request horizon in both verdict and expected-low selection. Cap overall confidence by support for the chosen future window and return neutral when the action depends on unavailable cells. Reject or mark unsupported horizons rather than extrapolating `90+` silently. Add sparse-current, sparse-future, disconnected-grid and dtd-365 tests.
- **Confidence:** high — contradictions follow from the specified omitted-point behavior.

### P4 — Observation count measures grid density rather than independent history
- **Severity:** high
- **Where:** SF-06 confidence rules; SF-06-build history/cohort construction; SF-03 fixture grid; E2 day-one claim.
- **What's wrong:** Counts are route/departure/fetch-day rows. Neighboring travel dates and repeated daily reads of the same cached quote inflate them. On a dense first-day route, a 30-day AP bucket already meets the 30-observation verdict floor; 17 complete days can supply 510 rows and qualify for high confidence at low CoV. This does not establish independent price evolution or seasonal coverage. A month/DOW cell can contain repeated observations of only a few actual departures.
- **Why it matters:** Frequent polling of a stale source reduces apparent volatility and increases confidence without adding information. High confidence can arrive before there is even one completed evaluation horizon. A 90-day fixture cannot establish annual repeatability.
- **Recommended fix:** Track unique fetch days, unique departure dates, age/identity of underlying source quotes where available, calendar span, and seasonal coverage separately from row count. Gate verdicts on minimum distinct collection days and supported horizons; cap confidence for cached/unknown-age data and seasonal fallback. Treat the existing thresholds as descriptive coverage bands until validated on held-out real outcomes. Record the coverage counts in `basis`, and test duplicated cached quotes and denser grids do not improve confidence by themselves.
- **Confidence:** high on the count inflation; medium on suitable replacement thresholds until real coverage/volatility data exists.

### P5 — Source switching and stale prices masquerade as market movement
- **Severity:** high
- **Where:** SF-06-build §3.2 prefer-itinerary collapse, §4.5 `latest_observed_price`; SF-05 stale/error flags; SF-07 current-price payload.
- **What's wrong:** Any itinerary beats every calendar observation in the group, regardless of freshness, price, stops or quality beyond rejection. The fixture adds a 0–8% itinerary premium only inside dtd 60. Crossing that boundary changes the measured product/source and can create a price jump without a market change. A scraper outage creates the reverse switch. Current-price resolution has no maximum acceptable age; `observed_price_age_seconds` and suspect flags disappear from feature frames and the response. The model groups only by route/date, so future non-economy/round-trip rows would also contaminate it unless explicitly filtered.
- **Why it matters:** A source returning after an outage looks like a price increase; an old cached bargain can be called a current bookable fare. Source errors become backtest wins/losses. The minimum of historical medians is an estimate of a typical level, not the expected minimum of future transaction prices.
- **Recommended fix:** Define the predicted quantity precisely, including currency, cabin/passengers/trip type, airport scope and any stop/baggage restrictions. Filter to it before collapse. Preserve source, price kind, freshness and quality provenance in the feature result. Model comparable source series separately initially, or require a validated cross-source normalization rule. Define a maximum current-price age per source; if unavailable/stale, return a note and neutral response rather than an actionable stale quote. Expose the chosen source and receipt/source-price timestamps. Label the curve and low as estimates of typical prices, without implying guaranteed availability.
- **Confidence:** high on specified source discontinuity and missing age policy; magnitude on real data requires matched source observations.

### P6 — Backtest rewards an oracle and allows the test data to be tuned to win
- **Severity:** blocker
- **Where:** SF-06-build §5 `BacktestSample`, scoring and “If the baseline does not beat…”; SF-06 Done when.
- **What's wrong:** For wait, `paid_minor` is the minimum future observed price, selected with hindsight. No purchase policy tells the simulated user when to buy. Any wait with a cheaper future price receives zero regret, even if the predicted window misses that price. The spec then instructs the agent to deepen fixture troughs/change their frequency if the model loses to always-book-now. Altering evaluation data to achieve a required win is fitting the test to the model. Fixing model thresholds does not make that valid.
- **Why it matters:** The portfolio can publish attractive regret/hit-rate numbers that no user following the recommendation could obtain. The expected-low window can be completely wrong without penalty.
- **Recommended fix:** Keep an explicitly named hindsight oracle only as a lower-bound comparator. Pin an executable wait policy before evaluation, such as purchasing on the first available quote meeting the predicted target within the announced window, otherwise at a defined deadline; specify missing-quote handling. Compute paid price from that policy, and score target/window error too. Freeze/version evaluation scenarios independently of results. Remove the “change fixture until win” instruction and the mandatory universal win gate; report losses. Use separate authored scenarios for branch correctness and genuinely held-out real periods for performance claims. Include always-book, a simple fixed-delay policy and the oracle in reports.
- **Confidence:** high — the lookahead payment and fixture-tuning instructions are explicit.

### P7 — The calibration report checks an identity and mishandles ties
- **Severity:** high
- **Where:** SF-06 L2 calibration done-when; SF-06-build §4.2, §5 and §6 `CalibrationBin`.
- **What's wrong:** Percentile rank is computed from a trailing sample and then “calibrated” against that same sample. This verifies arithmetic, not predictive calibration. The implementation uses a mid-rank for equal prices but the reported fraction counts strictly greater prices. With all prices equal, percentile is 50 and the strict greater fraction is zero, not 0.5. The phrase “p90 is beaten 10% of the time” also reverses cheap-price ranking if “beaten” means a lower price: roughly 90% are lower, 10% higher absent ties.
- **Why it matters:** A valid rank implementation fails a claimed calibration test on rounded/cached fares, or a meaningless in-sample statistic is presented as forecast validation.
- **Recommended fix:** Rename this output to historical-rank consistency and unit-test the rank formula directly. If reporting the complementary mid-rank, use `(greater + 0.5*equal)/n` and describe ties accurately. Score genuine forecast quantiles on future held-out comparable observations only if such quantiles are actually produced; the current rank is not a future probability. Remove automatic tolerance setting from the first successful run and predeclare what each metric measures.
- **Confidence:** high — an all-equal sample proves the mismatch algebraically.

### P8 — Walk-forward scoring lacks availability and censoring rules
- **Severity:** high
- **Where:** SF-06-build §3.2 and §5–6; `fetched_at`/`as_of` design; SF-05 historical quality context.
- **What's wrong:** A sample is retained whenever it has any future observation, even if most of its nominal 60-day window is beyond the dataset end or absent after an outage. Late fixture samples therefore compete on much shorter observed horizons. There is no exact decision timestamp or recorded data-availability/revision cutoff; `fetched_date <= as_of` is valid only for explicitly end-of-day decisions. A later quality correction could alter historical inputs without being visible as a later revision. The proposed leakage test checks a function argument, not which rows contribute to outputs.
- **Why it matters:** A single next-day observation can incorrectly label book-now successful although the unobserved later window contained a drop. An early-morning replay can consume observations fetched later that day. Recomputed historical quality can leak future information into the backtest.
- **Recommended fix:** Define decisions at a concrete instant, or explicitly end-of-day UTC for this daily baseline. Apply that cutoff to current-price lookup, historical features, and quality context. Preserve revision availability for replays. Require a completed horizon and minimum future coverage for primary scores; report censored/skipped counts and shorter-horizon metrics separately. Add adversarial future rows and assert predictions remain unchanged, not merely that `as_of` was passed. Split evaluation by time/departure cohort and report action coverage plus route/source/horizon strata; overlapping samples are not independent evidence.
- **Confidence:** high on missing rules; actual score bias cannot be measured before the harness and real data exist.
