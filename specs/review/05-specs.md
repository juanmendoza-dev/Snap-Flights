# Spec consistency and acceptance criteria

### Q1 — Documented open questions remain unresolved after code adopted answers
- **Severity:** medium
- **Where:** `specs/implementation/README.md` Open questions 1–5; SF-07 L2 example; SF-03 L2 outlier definition; `README.md`; `specs/README.md`; decision 0001 Consequences.
- **What's wrong:** L3 says its five questions are blocking/contradictory but implements recommended answers anyway, without an accepted disposition. SF-07 still shows percentile 34 with wait and a year of evidence; L3 uses the correct >=60 rule and actual history range. Root README says “No implementation yet,” and SF-03 remains “ready—do first.” Decision 0001 gives a serial ingestion-before-model order while other documents allow modeling immediately after SF-03. L0's one-tree ownership rule contradicts the actual multi-tree feature ownership design.
- **Why it matters:** An agent reading L0/L2 as authoritative can revert implemented fixes, repeat SF-03, or wait for ingestion unnecessarily. Reviewers cannot tell accepted decisions from provisional author suggestions.
- **Recommended fix:** Add accepted/superseded dispositions with dates and links for each open question. Update parent specs and examples in the same PR; do not leave contradictory examples as normative contract fixtures. Mark P0/SF-03 implemented at the reviewed commit and link L3 from the main spec index. Rewrite decision 0001's build-order note to reference the authoritative dependency graph. Replace “exactly one tree” with exclusive ownership of a declared set of paths plus a named shared-file change process.
- **Confidence:** high — directly contradictory/stale text remains in the reviewed tree. Owner approval history outside git was not provided.

### Q2 — Several supposedly executable instructions cannot be implemented literally
- **Severity:** medium
- **Where:** SF-06-build §2, §4.3–4.4, §5–6; SF-07-build Files owned/§5; implementation README open question 5.
- **What's wrong:** `build_reason()` must interpolate `rise_pct` and `horizon` but receives neither a curve/rise value nor config/horizon. The expected-low 1% band is a hardcoded threshold despite “every threshold is config-driven.” The advertised `python -m models.backtest` has no owned `__main__.py`. SF-07 owns `shared/routes.py` but does not pin its promised `Route`/loader contract. The outlier rationale contains a mathematical error: a price 85% below an expected level already 25% below the median is `0.15 * 0.75 = 0.1125` of the median, safely below 0.35, not above it. The general risk is an expected level substantially above the median.
- **Why it matters:** The implementing agent must invent parameters/files or duplicate hidden calculations while being told to execute the spec line by line and change nothing. Incorrect rationale gets treated as binding mathematical evidence.
- **Recommended fix:** Pass a typed numeric reason context containing the actual evaluated rise/drop, horizon and window into the renderer; generate prose from those same decision values. Add a named expected-low band setting. Own `models/backtest/__main__.py` and define its entry point. Pin the shared route loader now. Correct the outlier arithmetic while retaining the valid desire to test against the actual trailing gate denominator. Replace source-grep tests for magic numbers with behavior/config-change tests.
- **Confidence:** high — missing parameters/files and arithmetic are directly checkable.

### Q3 — The fixture is useful but its “realistic collection” claim is false
- **Severity:** high
- **Where:** SF-03-build §4.3; `scripts/gen_fixtures.py`; `data/fixtures/README.md`; SF-02 200/day cap; SF-04 tier cadence; SF-06 confidence/backtest acceptance.
- **What's wrong:** The fixture covers five fast-flights routes × 60 departure dates every day: 300 route/date queries' worth, beyond the proposed 200/day cap if one call handles one departure query. Calendar data is complete daily for all tiers, whereas real warm/cold routes run every three/seven days. It has no outages, missing queried dates, same-day conflicting versions, invalid canonical records, currency changes, or changing cache age for a reused source quote. It calls dtd<=60 the scheduler's restriction, but SF-04 does not specify that limit. The model's most fragile conditions are absent from its main acceptance dataset.
- **Why it matters:** Tests can verify medium/high coverage on data the scheduler is not budgeted to collect. Partial requeue and sparse seasonal fallback fail only after deployment. The fixture premium and fully populated date grid can make algorithm behavior look much cleaner than source behavior.
- **Recommended fix:** Keep the current dense fixture as a named deterministic happy-path dataset. Add a small operational scenario fixture driven by the actual tier cadence, explicit per-source date selection and request budget; include gaps, repeated cache quotes, source outages, reclassifications and noncontiguous date coverage. Run model/API thin-data acceptance against that fixture too. Do not change the dense fixture to force a backtest win. Measure live coverage before making availability or confidence promises.
- **Confidence:** high on tier mismatch and absent scenarios; the exact query budget comparison depends on the selected fast-flights API version's batching capability.

### Q4 — Statistical quality gates and alarms lack reproducible denominators
- **Severity:** medium
- **Where:** SF-05 record-level historical checks and run-level alarms; SF-04 due-route selection; `scripts/gen_fixtures.py:_inject_error_fares`; fixture gate tests.
- **What's wrong:** The quality spec does not define history cutoff, source/currency/trip-shape filtering, minimum sample count, zero-variance z-score behavior, or whether already suspect rows enter the reference distribution. Route-level median collapse alarms mix AP/date composition. `empty_run`, `coverage_drop` and `source_silent` do not distinguish scheduled work from intentionally not-due, disabled or cooling-down sources. The fixture's outliers are chosen relative to full-dataset medians, while a real trailing gate only knows the prefix at receipt time.
- **Why it matters:** A correctly sparse weekly schedule raises coverage alarms; a source not due today appears silent. A flat cached-price sample divides by zero in z-score logic. A quality agent can inadvertently use future fixture rows to prove a gate works.
- **Recommended fix:** Pin gate reference cohorts and an explicit as-of timestamp, exclude the incoming run from its own historical reference, and define minimum-history/zero-variance behavior. Compute alarms against planned/attempted coverage by source and tier, with separate “no work due” and “attempted but empty” outcomes. Compare like-for-like AP/travel-date cells for collapse alarms. Test each injected error against only the history available at that timestamp, and report when a statistical gate is unavailable rather than pretending it ran.
- **Confidence:** high on underspecification; actual alarm rates need live run histories.
